## #73 — HTTP MCP transport + expanded toolset

### Major

1. **Unrecognized `mcp { enabled <foo> }` value silently disables MCP**
   ([compile.rs:404](../../crates/croniq-config/src/compile.rs#L404)).
   The directive parser uses `matches!(a.value.as_str(), "true" | "yes" | "1" | "on")`
   to derive a `bool`. Any other value — including `"false"`, `"off"`, *or*
   typos like `enabled treu` — sets `cfg.enabled = false`. There is no
   warning path, no parse error, and no diff against the
   `McpConfig::default()` (which is `enabled: true`). A typo therefore
   silently disables the HTTP transport. The directive should accept a
   stricter set (`true|false`) and reject everything else with a parse
   error carrying `line`/`column`, mirroring how `parse_duration_secs`
   behaves after v0.5.0.

2. **Multiple `mcp { }` blocks shadow silently**
   ([compile.rs:413](../../crates/croniq-config/src/compile.rs#L413)).
   The compile loop overwrites `mcp = Some(cfg)` on each `Item::Mcp` it
   sees, so a Croniqfile with two `mcp { }` blocks keeps only the last —
   no error, no warning. Other top-level blocks (`server`, `pull_api`,
   `observability`) have the same property; this is consistent with the
   parser's "first match wins" patterns elsewhere but worth documenting,
   or rejecting outright at compile time.

3. **`MUTATION_TOOL_NAMES` is a manual list — drift risk**
   ([croniq-mcp/lib.rs:80](../../crates/croniq-mcp/src/lib.rs#L80)). The
   17 entries currently match the 17 `#[tool]`-decorated mutation
   functions in `tools.rs` exactly, so there is no live bug. But a future
   PR that adds a mutation tool without updating this constant would
   silently strip the `mcp:write` gate from that tool — a token with only
   `mcp:read` could call it. There is no compile-time check tying the two
   together. Mitigations: (a) emit `MUTATION_TOOL_NAMES` from a
   `build.rs` that scans `tools.rs` for `#[tool]` attributes, or
   (b) collocate the mutation flag on each tool fn (e.g. an attribute
   `#[tool(mutation = true)]`) and let the macro generate the list.

4. **Job timeout field accepts any string at PUT**
   ([api/jobs.rs:215](../../crates/croniq-server/src/api/jobs.rs#L215)).
   `handle_update` does
   `job.timeout = v.as_str().map(|s| s.to_string())` without parsing the
   duration. Garbage like `"foo"` or `"999999999h"` is persisted and only
   surfaces at execution time when the scheduler/runner tries to parse
   it. The CREATE path goes through the Croniqfile compiler which does
   validate duration strings (`parse_duration_secs`); the edit path
   should reuse that validator and return 400 on bad input. `max_retries`
   is stored as `u32` so JSON would already reject negatives, but no
   upper bound is enforced.

5. **Forecast move lacks an equivalence regression test**
   ([croniq-scheduler/src/forecast.rs](../../crates/croniq-scheduler/src/forecast.rs)).
   The function moved verbatim from `croniq-server::dashboard::compute_forecast`,
   and only one test (`empty_triggers_empty_buckets`) carried over. The
   bucketing math (`offset / bucket_size`, `iterations > 500`,
   per-bucket `jobs.contains(job_key)` dedup) is unverified for non-empty
   inputs after the move. Both the HTTP API and the MCP tool now call
   the same function, so any regression hits both surfaces. Add a test
   that exercises ≥3 fires across ≥2 buckets and asserts identical
   output between a direct call and a stubbed `dashboard_forecast` MCP
   handler.

### Minor

6. **`LocalSessionManager` has no documented TTL**
   ([croniq-mcp/lib.rs:135](../../crates/croniq-mcp/src/lib.rs#L135)).
   The factory uses `LocalSessionManager::default()`. A client that
   initializes a session over `/mcp` and never sends `DELETE /mcp` keeps
   that session in memory. rmcp's defaults are not inspected here, and
   the Croniqfile has no knob to bound it. Worth verifying upstream
   whether `LocalSessionManager` evicts on idle, and exposing a
   `mcp { session_ttl 30m }` directive if not.

7. **`check_mutation_scope` re-buffers the request body**
   ([mcp.rs:95](../../crates/croniq-server/src/mcp.rs#L95)). Every
   `POST /mcp` is fully buffered (up to `MAX_BODY_BYTES = 64 KiB`) so
   the JSON-RPC envelope can be inspected, then the body is wrapped
   into a fresh `Request`. For tool-call traffic this is fine — MCP
   payloads are tiny — but the streaming guarantee is lost. If
   server-streaming tools are added later, the buffering will need to
   move to a shape-aware predicate that only inspects the headers /
   first chunk.

8. **Croniqfile `mcp { }` rejects no unknown directives**
   ([compile.rs:406](../../crates/croniq-config/src/compile.rs#L406)).
   `mcp { foo bar }` is silently ignored. Other blocks
   (e.g. `observability`) accept their own grab-bag of nested directives,
   so this is consistent — but a strict-mode warning for unrecognized
   keys would catch typos and is cheap.

### Note

9. **MCP scopes are coarse-grained by design**
   ([mcp.rs:1-14](../../crates/croniq-server/src/mcp.rs#L1)). A token
   with `mcp:write` can call any mutation tool over `/mcp`, including
   `update_job` — without holding the corresponding `jobs:write` HTTP
   API scope. This is the documented behavior (README's *MCP server*
   section), and the model is "MCP is a separate gate". If the project
   later wants per-tool scope enforcement (so `update_job` requires
   both `mcp:write` and `jobs:write`), it would be a behavior change,
   not a bug fix.

## #72 — Editable jobs / calendars / api-clients

### Minor

1. **Last-writer-wins on concurrent `PUT`**
   ([api/jobs.rs:201](../../crates/croniq-server/src/api/jobs.rs#L201),
   [api/calendars.rs](../../crates/croniq-server/src/api/calendars.rs),
   [api/auth_endpoints.rs](../../crates/croniq-server/src/api/auth_endpoints.rs)).
   The edit handlers read-modify-write through `create_job_definition`
   (and equivalents) without optimistic concurrency: no ETag, no
   `updated_at` precondition, no version column. Two simultaneous
   admin clients editing the same job will see one silently overwrite
   the other. Realistic only for multi-admin setups; flagging because
   the editable surface is new and the door is open to add `If-Match`
   without breaking existing clients.

2. **`CalendarPicker` ambiguity: name vs UUID**
   ([ui/components/ui/calendar-picker.tsx:33](../../ui/src/components/ui/calendar-picker.tsx#L33)).
   The picker's `value` is the calendar **name** as a string. The
   server accepts the same shape via the `calendar` field on
   `RegisterJobRequest` / `UpdateTriggerRequest`. Names are unique today
   but are also user-editable, so a future "rename calendar" feature
   would orphan stored references. Either store calendar UUIDs in the
   schedule row or document the rename-is-rebind contract.

### Note

3. **`PATCH` semantics are JSON-presence based**
   ([api/jobs.rs:209](../../crates/croniq-server/src/api/jobs.rs#L209)).
   The handler distinguishes "key absent" (leave as-is) from "key set
   to `null`" (clear) by dropping into raw `serde_json::Value` instead of
   a typed struct. This is the right call — typed structs collapse the
   two cases into one — but it deserves a comment-block reference for
   future maintainers since the pattern is unusual in this codebase.

## Cross-cutting

1. **MCP gating is enforced at three different layers** — the HTTP
   transport middleware (`mcp:read` / `mcp:write`), the `CroniqMcp`
   factory (`mutations_enabled` flag controls whether mutation tools
   are *registered*), and the individual `#[tool]` body (per-tool DSL
   ownership checks via `JobError::DslManaged`). The layers compose
   correctly today, but the contract between them is implicit. A short
   architecture note in `crates/croniq-mcp/src/lib.rs` would help —
   answering "where does scope X get enforced and what fails first?".

2. **No CHANGELOG discipline check in CI**. Both v0.6.0 and v0.7.0 were
   tagged with an empty `[Unreleased]` section. The CHANGELOG was
   backfilled for v0.7.0 in this same PR, but a CI gate (e.g. require a
   non-empty `[Unreleased]` block on every PR that touches `crates/`)
   would prevent silent drift in the future. Out-of-scope for this
   review, but worth filing.

## Followups recommended

In priority order:

1. **Reject unknown values in `mcp { enabled }`** — turn the silent-disable
   path into a parse error with `line`/`column`. Two-line change in
   `croniq-config/src/compile.rs`.
2. **Validate `timeout` in `PUT /v1/jobs/{key}`** — call the existing
   `parse_duration_secs` from `handle_update` and return 400 on failure.
3. **Add forecast bucketing tests** — at minimum, a non-empty case and a
   window-clamp case in `croniq-scheduler/src/forecast.rs`.
4. **Auto-generate `MUTATION_TOOL_NAMES`** — either a `build.rs` scan or
   a `#[tool(mutation = true)]` macro flag, so the constant cannot drift
   from the registered tools.
5. **Add ETag / `If-Match` to PUT endpoints** — only if real concurrent
   admin editing materializes; defer until needed.
